n8n retry safety: when “Retry On Fail” can create duplicates

Automatic retries improve availability only when repeating the operation is safe. The dangerous case is uncertainty: the workflow timed out, but the remote system may already have completed the action.

The failure that matters

Imagine a workflow sends a create-order request. The remote service saves the order, but the response is lost. n8n sees a timeout and retries. Without idempotency, the second request can create a second order.

Use one operation identity

When an API supports idempotency, derive a stable key from the business operation and reuse it across retries. Do not generate a fresh key for each attempt. A new intended operation should receive a new key.

Do not stack retry layers blindly

Node-level retries, scheduler retries, manual reruns, webhook redelivery, and upstream retries can interact. Document which layer owns retry behavior and what makes a repeated attempt safe.

Test the ambiguous cases

  • the first request definitely failed before reaching the destination;
  • the destination completed the write but the response was lost;
  • two copies run concurrently;
  • the first attempt completes only part of the workflow;
  • a human manually retries the execution later.
Evidence beats “it should be fine.”
