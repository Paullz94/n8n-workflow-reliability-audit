n8n webhook duplicates: 5 reliability checks before production

Webhook retries are normal. Duplicate payments, CRM writes, emails, or database inserts are not. The important question is whether a repeated delivery can safely run through the workflow again.

1. Use a stable event identifier

Prefer an event or delivery ID supplied by the source. If the same business event arrives twice, both deliveries need to resolve to the same idempotency key. A workflow execution ID is usually not enough for cross-execution deduplication because a replay can create a new execution.

2. Reserve the event before the side effect

A simple “check whether this ID exists, then insert it” pattern can still race when two copies arrive at the same time. For business-critical writes, use an atomic uniqueness or reservation mechanism so only one execution can claim the operation.

3. Separate seen from completed

Marking an event as processed before the external action finishes can prevent duplicates while also losing the intended action after a crash. Track enough state to distinguish received, claimed, completed, and retryable failures.

4. Retry outbound requests only when they are safe to repeat

n8n supports retry controls for HTTP requests, but a retry can repeat a POST or PATCH that already succeeded remotely. When the destination supports idempotency keys, keep the same stable key across retries. Otherwise, design a deduplication or reconciliation step before enabling automatic retries.

5. Make exhausted retries visible

Retries should end in a traceable failure path. Route failures into an error workflow, queue, alert, or recovery process that preserves the operation key and enough context to safely decide whether to retry.
