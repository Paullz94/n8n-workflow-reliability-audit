# Launch Sequence — Human, Platform-Native, Capacity-Bounded

Updated: 2026-09-25

This is an operational sequence, not an anti-detection cadence.

## Principle

Do not launch everywhere at once just because tooling makes it possible. Activate one permitted distribution surface, observe whether the offer and support flow work, then add another independent channel only when it improves learning or reach.

## Sequence

### 1. Technical public asset
- Keep the isolated GitHub branch as source-of-truth.
- Deploy the local browser preflight only after a legitimate static-host activation path is available.
- Publish synthetic examples only; never customer files.

### 2. Direct checkout
- Activate a legitimate Stripe account/connection.
- Create the EUR 149 pilot product/payment link.
- Do not pay for a custom Stripe domain.
- Run only Stripe test mode before going live; test-mode payments never count as revenue.
- Reconcile live payments through the provider adapter/ledger.

### 3. First marketplace
Choose one marketplace where Paul already has or is willing to create a legitimate profile. Complete the platform's real identity/profile/KYC requirements.

- Post one accurate fixed-scope offer.
- Keep communication/payment on-platform where required.
- Observe qualified inquiries, objections, delivery burden and refunds.
- Do not create repetitive listings to multiply exposure.

### 4. Second independent channel
Only after the first channel's support load remains bounded:
- add a different marketplace/direct channel;
- adapt the listing to that platform rather than duplicating mechanically;
- keep measurement by source.

### 5. Iteration
Use actual qualified objections and paid-delivery friction to decide:
- which scanner rules to add;
- whether EUR 149 is understood;
- whether the free preflight qualifies leads;
- whether the re-scan creates too much support work.

## Make Community exception

Do not use autonomous AI-generated posting there under current rules. It remains a research source unless Paul independently authors an original permitted contribution/listing.

## Scale gate

Increase acquisition volume only when:
- checkout works;
- delivery succeeds without Paul as daily operator;
- support remains bounded;
- no platform-policy warning exists;
- real conversion/objection data justifies expansion.

Never increase volume merely to make activity look organic or to avoid automated-abuse detection.
