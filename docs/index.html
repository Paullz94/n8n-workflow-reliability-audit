What PCFlows looks for

Failures that matter to the business, not just the editor.

The audit is deliberately narrower than a generic blueprint linter. It focuses on whether failure and recovery behavior can create missing, duplicated or misleading business outcomes.

×2

Duplicate effects

Retries, repeated webhooks and non-idempotent writes that can create the same side effect twice.

Ø

Silent skips

Filters and handlers that let a run appear healthy while expected business work never happened.

↺

Recovery gaps

Missing error routes, incomplete-execution settings and rollback boundaries that complicate recovery.

⇄

Race conditions

Parallel runs and ordering assumptions that can overwrite or reorder state unexpectedly.

Evidence, not a mystery score

Every important finding should answer four questions.

Example: retrying external write

A retry is not automatically bad. The audit asks whether repeating that specific side effect is safe.

MEDIUM · PREVENT

Evidence
The write-like module has automatic retry behavior.
Why it matters
The first attempt may have committed before the failure became visible, so retrying can duplicate the side effect.
Next step
Use an idempotency key, upsert/deduplication guard or equivalent destination-specific protection.
Verify
Replay the same synthetic business event and confirm only one intended effect remains.

Boundaries

What PCFlows does not pretend to prove.

A blueprint is structural evidence, not a live production system. PCFlows does not claim that a clean static audit proves runtime correctness, valid credentials, healthy third-party APIs, complete business logic or legal/security compliance.
