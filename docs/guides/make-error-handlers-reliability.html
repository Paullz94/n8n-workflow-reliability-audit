Reliability guide · Make.com

Error handlers can save a scenario — or hide the failure.

Make.com gives you several error-handler directives. They are powerful, but each one changes what “success”, “failure” and “recovery” mean for the business process. The important question is not simply “does this scenario have an error handler?” It is:

What happens to the business event when this module fails?

This guide focuses on reliability and data integrity rather than on generic Make best practices. The examples below are intentionally conceptual; verify behavior against your own sanitized scenario and synthetic test data.

Why a green scenario is not enough

An automation can finish without a visible platform-level failure while still missing the business outcome you cared about. For example, a CRM write can fail, an error handler can let processing continue, and later modules can still succeed. The technical run is not the same thing as the business transaction.

That is why PCFlows treats error directives as reliability semantics, not just exception-handling syntax.

Skip / Ignore

Potential silent lossDetect

Make's Skip/Ignore behavior can drop the failed bundle and continue processing later bundles. That can be completely intentional — for example, when one malformed optional record should not stop an entire batch.

The risk appears when the skipped item represents business work that must happen exactly once: creating an invoice, updating an order, booking a lead, or recording a payment-related state change.

Ask:
  • Is losing this failed event acceptable?
  • Can an operator see that it was skipped?
  • Is there a quarantine or reconciliation path?
  • Could the overall scenario still look successful while the business action is missing?

Safe verification: force a synthetic failure on the affected module and confirm the missing business action is visible somewhere operators actually monitor.

Resume

Potential silent successDetect

Resume can provide substitute output for a failed module and allow downstream processing to continue. That is useful when a fallback value is genuinely part of the design.

But a fallback can also blur the line between “the external write succeeded” and “we manufactured enough output to keep the rest of the scenario moving”.

Ask:
  • Can downstream modules distinguish real output from fallback output?
  • Could a success notification be sent even though the important write failed?
  • Is the fallback safe for every consumer downstream?

Safe verification: make the write fail on synthetic data, then inspect downstream behavior. Verify that nobody can interpret substitute output as proof the side effect happened.

Commit

Partial stateRecover

Commit is about preserving transactional changes before stopping the current run. Partial state is not automatically wrong; sometimes it is exactly what you want.

The reliability question is whether that partial state is understood and reconcilable.

Ask:
  • Which earlier changes are intentionally kept?
  • Can you identify records that stopped halfway through the larger process?
  • Is there a compensating action or reconciliation job?

Safe verification: create a synthetic case where an earlier transaction completes and a later step fails. Confirm operators can identify the boundary between committed and unfinished work.

Rollback

Transaction boundaryRecover

Rollback is only as broad as the transaction boundary Make and the underlying modules can actually undo. Make documents an important limitation: previously committed changes cannot be rolled back later.

This becomes especially important when scenario settings automatically commit work along the way.

Ask:
  • Which modules are truly transactional?
  • Has earlier work already been committed?
  • Does the team assume rollback means “undo everything” when it cannot?

Safe verification: force a later failure after an earlier transactional step and observe exactly what state remains.

Break and retry

Duplicate-effect riskPrevent

Retry is essential for transient failures, but external writes are where retry becomes dangerous. A request may have reached the remote system successfully even if the caller never received a clean response.

If you retry blindly, you can create the same side effect twice.

Ask:
  • Does the destination support idempotency keys?
  • Can you upsert by a stable business key?
  • Can the write be safely repeated?
  • Do you know whether the first attempt committed before the error became visible?

Safe verification: replay the same synthetic event and confirm the intended external state exists only once.

Scenario-level settings matter too

Sequential vs parallel

Instant webhook scenarios can process events concurrently. If multiple events touch the same logical record, ordering and race behavior become part of your data-integrity design.

Incomplete executions

Recovery settings determine whether failed work remains available to inspect and resume. For workflows with important writes, recovery design should be explicit rather than accidental.

A practical review sequence

  1. Identify every module that changes external state.
  2. Trace each module's error route.
  3. Classify the handler: stop, skip, substitute, retry, commit or rollback.
  4. Ask what business state remains after that behavior.
  5. Define how an operator would notice missing or partial work.
  6. Test the failure with synthetic data.
  7. Re-run the static review after remediation.
